§0

The agent loop

A mental model that lasts all day

§0 · The agent loop

What makes it “agentic”?

Not autocomplete. Not chat. The model acts in a loop, with tools.

  • act — read and write files, run commands, run tests
  • observe — read the output: errors, test results, diffs
  • revise — adjust and go again, until the goal is met
  • goal
  • plan
  • act
  • observe
  • revise
Introduce the loop BY NAME; we refer back to it all day. The agent isn't magic — it's this loop, plus your tools and your steering. Point at the rail: you will see it again in §5, where the same five beats become plan, test, implement, review, ship.

§0 · The agent loop

Vibe-coding vs. AI-assisted engineering

Vibe-coding

Prompt, accept, hope

You read little

Disciplined use

Plan, verify, review

You own architecture & review

Studies of professional developers: they plan before implementing and validate every output.
Reassure the physicists: you stay in control. The agent types; you decide and check. This framing recurs in §5.

§0 · The agent loop

When to delegate

Agents shine on small, well-specified tasks. They struggle where architectural judgement is needed.

✓ Delegate

“Add an RK4 step and test its convergence order.”

✗ Decide yourself

“Redesign how the solver handles stiff systems.”

Today’s task is deliberately small — and that is the point.

Teach the triage instinct. Part of the skill is recognizing what NOT to hand off. Ask: what is the smallest piece of your own work that would pass the left-hand test?

§2

uv crash course

The substrate: reproducible environments

§2 · uv

Why uv?

One fast tool for environments + packages + running.

  • Reproducible: one locked uv.lock that everybody shares
  • No manual venv juggling
  • uv run = “run this inside the project’s environment”

direnv

Activates the environment when you cd in.

UV_CACHE_DIR

One shared cache — point it at fast local disk, not $HOME on a network mount.

Keep it short — uv isn't the point, it's the substrate. Reproducibility ties directly to good scientific practice: the lockfile is what makes "it worked on my machine" a checkable claim. The UV_CACHE_DIR tip matters on cluster home directories.

§2 · uv

The four commands you need


uv sync                              # create/refresh the env from pyproject + lock
uv run pytest                        # run something inside that env
uv run python scripts/run_decay.py   # same, for a script
uv add matplotlib                    # add a dependency

These four cover ~95% of daily use. Everything today runs through uv run.

§4 · Steering the agent

CLAUDE.md — project memory

Instructions Claude reads every session: conventions, how to run things, gotchas.

The concision test

For each line ask: “would removing this cause a mistake?” If not — cut it.

Bloated CLAUDE.md files get ignored — the rules that matter drown in the noise.
Concision over completeness is THE lesson here. Show odelab's short CLAUDE.md as the model, and be honest that the failure mode is writing a style guide nobody — human or model — reads.

§4 · Steering the agent

Skills — instructions on demand

CLAUDE.md is always loaded. A skill loads only when it is relevant — which keeps both short.

Install

Use a published skill from a marketplace or a colleague.

Invoke

Claude picks it up by description, or you name it directly.

Write your own

A folder, a Markdown file, a description. That is the whole format.

Good first candidates: your plotting conventions, your docstring style, your group’s slide template.

Split out from the original "More levers" slide — skills deserve their own beat, they are the main customization lever people take home. Show one real skill directory live: SKILL.md with frontmatter, nothing more.

§4 · Steering the agent

Permissions & how hard it thinks

plan mode
read-only. Explore anything, change nothing.
normal
asks before each edit or command.
accept edits
edits freely, still asks for commands. Fast, needs a clean git tree.
/permissions
the allowlist — grant uv run pytest once, stop being asked.

Reasoning effort

More thinking for genuinely hard, ambiguous tasks; less for routine edits. Not “biggest by default” — it costs time, and a well-specified task rarely needs it.

Keep the agent on a leash you have consciously chosen — a dirty git tree is the one thing that makes a mistake expensive.

Split out from "More levers", with the model/effort question folded in as one card rather than its own module. Demo /permissions live. The safety message: your real protection is git, not the permission prompt.

§5 · Ship a feature

The task: add RK4

Add a 4th-order Runge–Kutta step alongside Euler — and prove it is better.

The canonical Claude workflow is Explore → Plan → Code → Commit. The test-first and explicit review steps are our deliberate additions — well supported, and the reason this works on numerical code.
  • plan
  • test
  • implement
  • review
  • ship
Set the arc. Same five beats as the agent loop from §0 — point back at it. Short input before each phase, then they work. Total 46 minutes; announce that you will call the phase changes out loud.

§5 · Phase 1

Plan

Get a plan before any code. Plan mode, or a brainstorming pass.

  • Have Claude draft the plan
  • Read it. Annotate it. Then: “address all my notes, do not implement yet”
  • Do not let it code until the plan is one you would sign off on
  • plan
  • test
  • implement
  • review
  • ship
The annotation trick prevents premature coding — Claude tends to jump straight to implementing. "Do not implement yet" is the phrase to teach; make them say it out loud.

§5 · Phase 1

Your turn

Plan RK4

In plan mode: plan adding an rk4_step to odelab, reusing the existing integrate(..., method=...) hook.
  • Review the plan and add a note or two of your own
  • Tell it to revise the plan — without coding yet

Done whenyou have a plan you would sign off on.

Circulate and read plans over shoulders. Common failure: the plan silently invents a new dispatch mechanism instead of reusing the method= hook — good teaching moment about being specific.

§5 · Phase 2

Test first — red

Give the agent a pass/fail check it can run itself. For numerical code, that is a test.

Accuracy

RK4 matches the analytic decay to a tight tolerance.

Convergence order ≈ 4

Double the steps → the error drops ~16×. Euler only manages ~2×.

  • plan
  • test
  • implement
  • review
  • ship
Contrast with test_euler_is_first_order in the repo — it already asserts the ~2x factor, so they have a template. The convergence-order test is the real property to assert: it pins the method, not just one number.

§5 · Phase 2

Your turn

Write the failing test

Add tests for rk4_step before implementing it — matching the analytic solution, and checking the convergence order.

uv run pytest -q     # should be RED — rk4_step does not exist yet

Done whena new test exists and fails for the right reason.

"Fails for the right reason" matters: an ImportError is the expected red, a passing test means the test is wrong. Check a few screens for tests that assert nothing.

§5 · Phase 3

Implement — green

Now let Claude implement, and let the tests close the loop.

Editing odelab/integrators.py…
Running: uv run pytest -q
FAILED test_rk4_convergence_order — factor 8.1, expected ~16
The k3 term used dt instead of dt/2. Fixing…
6 passed

Without a runnable check, “looks done” is the only signal — and you become the verification loop.

  • plan
  • test
  • implement
  • review
  • ship
This is the payoff of the self-verifying loop: observe → revise, driven by pytest rather than by you. Let them watch Claude iterate. Point out that the failure message did the teaching, not the human.

§5 · Phase 3

Your turn

Make it green

Implement rk4_step until my tests pass.

uv run pytest -q

Done whenall tests pass, including your convergence-order test.

Hands off the keyboard where possible — the point is watching the loop run itself. If someone is stuck in a correction spiral, that is failure pattern 2 from §6: /clear and reprompt.

§5 · Phase 4

Review

Two reviewers: the agent, and you.

  • /code-review, or ask Claude to review its own diff adversarially
  • Read the diff yourself — correctness first, then clarity
  • Request changes; re-run the tests
Do not merge what you did not read.
  • plan
  • test
  • implement
  • review
  • ship
Universally recommended across every serious source: validate the output. "Adversarially" is the useful word — asking "is this correct?" invites agreement, asking "find what is wrong with this" does not.

§5 · Phase 4

Your turn

Review the diff


git diff
Review your change for correctness and clarity — find what is wrong with it.

Then read it yourself and request one improvement.

Done whenyou have read every changed line and the tests still pass.

Insist on the human read. Ask afterwards: who found something Claude's own review missed? Usually at least one person has an unnecessary helper or a docstring that contradicts the code.

§5 · Phase 5

A small, targeted PR


git switch -c add-rk4
git add -A
git commit -m "Add RK4 integrator + convergence tests"
git push -u origin add-rk4

You will not meaningfully review a 1000-line PR. Neither will your colleagues. Keep it small — that is what makes agent-written code safe to merge.

  • test
  • implement
  • review
  • ship
Adjust the remote flow to your GitHub setup (fork-per-person vs shared org repo) — confirm this before the session. Open the PR in the browser so they see CI run the tests.
